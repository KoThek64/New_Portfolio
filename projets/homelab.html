01 — Architecture

Un service par conteneur.

Chaque service tourne dans son propre conteneur LXC (Debian 13, non privilégié). Seul Caddy est joignable depuis Internet, et aucun conteneur ne peut contacter les autres machines de la maison. Avec tout allumé, Cuby utilise environ 2 Go de RAM sur 16 et moins de 2 % de CPU.

02 — En détail

Comment ça tient.

// dns

Une IP qui change plusieurs fois par jour

La box 5G change d'IP publique régulièrement. Un script Bash, lancé chaque minute par un timer systemd, met à jour le domaine via l'API Netlify. Il crée le nouvel enregistrement avant de supprimer l'ancien.

// sécurité

Plusieurs barrières

Pare-feu Proxmox en « tout refuser sauf », conteneurs isolés du réseau local, CrowdSec qui bannit les IP suspectes via nftables, mises à jour de sécurité automatiques. Les premiers robots sont arrivés moins d'une heure après la mise en ligne.

// ci

La CI, et GitHub en vitrine

Le runner exécute dans Docker la CI de tous mes dépôts Forgejo. Quand main avance, la version stable est copiée sur GitHub ; pour un tag, une release est créée avec ses notes. La copie n'est jamais forcée : en cas d'écart, le job échoue.

// exploitation

Sauvegardes et supervision

Sauvegardes vzdump quotidiennes de Forgejo et Caddy, hebdomadaires pour Minecraft. Uptime Kuma vérifie que la forge répond et surveille le certificat ; les alertes arrivent par ntfy.

Depuis, la box 5G fait le routage et OPNsense n'est plus utilisé.
