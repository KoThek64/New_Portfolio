03 — Zoom technique

Personne ne voit le budget des autres.

Un filtre sur toutes les lectures

Les données d'un budget sont sensibles. Plutôt que de compter sur chaque requête pour penser à filtrer par utilisateur, un filtre SQL Doctrine ajoute la condition automatiquement à toute lecture d'une entité qui appartient à un compte.

Il est armé au début de chaque requête HTTP. Et s'il n'y a pas d'utilisateur connecté, il ne renvoie rien plutôt que tout : une isolation qui échoue doit échouer fermée.

src/Doctrine/Filter/OwnerFilter.php php
final class OwnerFilter extends SQLFilter
{
    public const string NAME = 'owner';
    public const string PARAMETER = 'user_id';

    public function addFilterConstraint(ClassMetadata $targetEntity, string $targetTableAlias): string
    {
        if (!$targetEntity->reflClass->implementsInterface(OwnedByUser::class)) {
            return '';
        }

        // Filtre armé sans utilisateur (visiteur anonyme) : on ne renvoie rien
        // plutôt que tout — une isolation ne doit jamais échouer en s'ouvrant.
        if (!$this->hasParameter(self::PARAMETER)) {
            return '1 = 0';
        }

        $column = $targetEntity->getSingleAssociationJoinColumnName('user');

        return sprintf('%s.%s = %s', $targetTableAlias, $column, $this->getParameter(self::PARAMETER));
    }
}

Tester l'attaque, pas seulement le cas normal

Les identifiants sont des UUID, impossibles à deviner. Mais le test suppose le pire : Alice connaît l'identifiant d'une catégorie de Bob. Même ainsi, la ligne ne remonte pas de la base.

De la même façon, le propriétaire d'une donnée n'est jamais lu depuis un formulaire, que le client pourrait modifier : il est posé côté serveur au moment de l'enregistrement.

tests/Functional/OwnerFilterTest.php · extrait php
public function testForcingAnotherAccountsUuidFindsNothing(): void
{
    $alice = $this->createUser('alice@my-money.test');
    $bob = $this->createUser('bob@my-money.test');
    $bobCategoryId = $this->createCategory($bob, 'Loyer')->getId();
    self::assertInstanceOf(Uuid::class, $bobCategoryId);

    $this->browse('/', $alice);

    self::assertNull($this->entityManager()->find(Category::class, $bobCategoryId));
}
04 — Modèle de données

Cinq entités, des garde-fous en base.

Les règles importantes ne vivent pas que dans le PHP : elles sont aussi écrites dans PostgreSQL. Un montant ne peut pas être négatif, supprimer un compte efface toutes ses données, et un même objectif ne peut pas exister deux fois. Des tests d'intégration vérifient que la base refuse bien ce qu'elle doit refuser.

PostgreSQL 16 Doctrine ORM 3 · identifiants UUID
User Le compte. Sa suppression part en CASCADE sur tout ce qui lui appartient
Category Dépense ou revenu, avec couleur et icône ; archivable plutôt que supprimée
Transaction Montant en centimes, libellé, date ; suppression douce, index partiels sur les lignes actives
Recurrence Opération mensuelle : jour du mois et dernier mois généré, pour ne jamais la créer deux fois
Goal Plafond global, plafond par catégorie ou épargne ; unicité garantie par des index partiels
05 — Méthode

Travailler comme en équipe.

Même seul, chaque changement passe par une pull request de dev vers master, et rien n'est fusionné tant que la CI n'est pas verte. Un hook Git impose une convention de message et un temps passé par commit ; un workflow additionne ces temps et les publie sur chaque pull request.

Commit

Hook commit-msg : feat(auth): … @1h30

Pull request

De dev vers master, rapport de temps automatique

Qualité

php-cs-fixer, PHPStan niveau 6, Rector

Tests

PHPUnit sur un vrai PostgreSQL 16

Fusion

dev réaligné automatiquement sur master
