01 — Contexte

Un jeu pour pratiquer l'objet.

Après Suivi des dépenses, je voulais un projet Kotlin plus riche, avec beaucoup de règles métier à modéliser. Un combat Pokémon en est rempli : statistiques calculées selon le niveau, 18 types et leurs faiblesses, points de pouvoir, ordre d'attaque selon la vitesse.

Le projet a évolué par étapes. D'abord des données en fichiers JSON écrits à la main pour quelques Pokémon, puis un import automatique depuis PokéAPI vers une vraie base PostgreSQL, installée dans un conteneur de mon homelab. Le développement est aujourd'hui en pause, sans reprise prévue : le combat fonctionne, et la suite (évolutions, capture, statuts, zones à explorer) reste listée dans la roadmap du dépôt. Si je reprends l'idée, ce sera peut-être directement dans un moteur de jeu comme Unity.

03 — Zoom technique

Dans le code.

La formule des dégâts

Selon la catégorie de la capacité, on oppose l'attaque à la défense (physique) ou l'attaque spéciale à la défense spéciale. Une capacité de statut ne fait pas de dégâts.

Le résultat est ensuite multiplié par le bonus de type identique (STAB, ×1,5), l'efficacité contre les deux types du défenseur (de ×0 à ×4) et un facteur aléatoire entre 85 et 100 %.

modeles/classes/Combat.kt kotlin
private fun calculerDegat(attaquant : Pokemon, defenseur : Pokemon, idCapacitee : Int) : Int {
    // On récupère les données de la capacité
    val capData = MoveRepository.getParId(idCapacitee)

    val a : Int
    val d : Int

    val typeDefenseur1 = defenseur.espece.types[0]
    val typeDefenseur2 = if(defenseur.espece.types.size > 1) defenseur.espece.types[1] else null

    when (capData.categorie) {
        CategorieCapacitee.PHYSIQUE -> {
            a = attaquant.stats.attaque
            d = defenseur.stats.defense
        }
        CategorieCapacitee.SPECIALE -> {
            a = attaquant.stats.attaqueSpe
            d = defenseur.stats.defenseSpe
        }
        CategorieCapacitee.STATUS -> return 0
    }

    val puissance = (capData.stats.puissance ?: 0).toDouble()
    val niveau = attaquant.niveau.toDouble()

    // Formule de dégâts officielle
    var degatsBase = (floor(2.0 * niveau / 5.0 + 2.0).toInt() * puissance * a.toDouble() / d.toDouble())
    degatsBase = floor(degatsBase / 50.0) + 2.0

    // STAB + Efficacité
    val stab = if (attaquant.espece.types.contains(capData.type)) 1.5 else 1.0
    val efficaciteType = CalculEfficacite.getEfficaciteType(capData.type, typeDefenseur1, typeDefenseur2)
    val aleatoire = Random.nextDouble(0.85, 1.0)
    val critique = 1.0

    return floor(degatsBase * stab * efficaciteType * aleatoire * critique).toInt()
}

Importer 151 Pokémon depuis PokéAPI

Au premier lancement, le seeder interroge l'API pour chaque numéro. Les appels réseau passent par Ktor dans des coroutines, et les réponses JSON sont désérialisées dans des DTO.

Il est idempotent : s'il est interrompu, il reprend là où il s'était arrêté en sautant les Pokémon déjà en base, et une erreur sur un Pokémon n'arrête pas l'import des autres. Le nom français vient de la ressource species.

service/PokemonSeeder.kt · extrait kotlin
suspend fun seedPokemon(range : IntRange = 1..151){
    if (isSeeded(range.count())) {
        println("✅ Pokémon déjà importés, seeding ignoré.")
        return
    }
    println("Début de l'importation")

    val existingIds = transaction {
        PokemonTable.slice(PokemonTable.id)
            .selectAll()
            .map { it[PokemonTable.id] }
            .toSet() // On stocke dans un Set pour une recherche rapide
    }

    for (id in range){
        if (id in existingIds) {
            continue
        }

        try {
            val pokemonDto: PokemonDto = client.get("https://pokeapi.co/api/v2/pokemon/$id").body()

            val speciesDto: PokemonSpeciesDto = client.get("https://pokeapi.co/api/v2/pokemon-species/$id").body()
            val nomFr = speciesDto.names.find { it.language.name == "fr" }?.name ?: pokemonDto.name

            transaction {
                PokemonTable.insertIgnore {
                    it[PokemonTable.id] = pokemonDto.id
                    it[nom] = nomFr
                    // … statistiques et types
                }
            }
            println("[#$id] $nomFr ajouté à la base")
        } catch (e : Exception){
            println("Erreur lors de l'import du pokémon ID $id : ${e.message}")
        }
    }
    println("Importation terminée !")
}

Les actions, typées

Une action de combat est une classe scellée : le compilateur connaît tous les cas possibles et vérifie qu'un when les traite tous. Ajouter une action (un objet, par exemple) signale chaque endroit à mettre à jour.

modeles/ActionDeCombat.kt kotlin
sealed class ActionDeCombat {
    data class Attaque(val capacitee: CapaciteeApprise) : ActionDeCombat()
    data class ChangerDePokemon(val index : Int) : ActionDeCombat()
    object Fuite : ActionDeCombat()
}
04 — Architecture

Comment c'est construit.

Le code est découpé par responsabilité : les modèles portent les règles du jeu, les repositories lisent la base, les seeders la remplissent depuis l'API. Les identifiants de connexion sont lus dans un fichier db.properties exclu de Git.

05 — Qualité

Tester les règles du jeu.

Les limites, d'abord

15 tests JUnit 5 couvrent les niveaux, les capacités (apprendre, oublier, doublons), les soins et les dégâts. Ils visent surtout les bornes : monter jusqu'au niveau 100 doit marcher, le dépasser doit lever une exception métier.

Ils tournent sur GitHub Actions à chaque push et pull request : build Gradle, tests, publication des résultats dans la pull request et rapport HTML conservé.

src/test/kotlin/NiveauTests.kt kotlin
@Test
fun monterDeNiveauJusqua100(){
    salameche = Pokemon.creer(salamecheE, 1, capaciteeDex)
    for(i in 1 until 100){
        assertTrue { salameche.monterDeNiveau() }
    }
    assertTrue { salameche.niveau == 100 }
}

@Test
fun monterDeNiveauAuDessusDe100(){
    salameche = Pokemon.creer(salamecheE, 100, capaciteeDex)
    assertThrows<NiveauException> { salameche.monterDeNiveau() }
    assertTrue { salameche.niveau == 100 }
}

06 — Bilan

Ce que j'en retiens.

01

Modéliser avant de coder

Interface commune au joueur et à l'adversaire, classe scellée pour les actions, exceptions métier : le langage aide à rendre les états impossibles impossibles à écrire.

02

Du fichier à la base

Passer de JSON écrits à la main à PostgreSQL rempli par une API m'a fait toucher à l'ORM, aux appels réseau asynchrones et à la reprise sur erreur d'un import.

03

L'outillage dès le départ

Tests, CI, conventions de commit, guide des issues : mettre ces règles en place tôt rend les changements suivants moins risqués, même sur un projet personnel.
